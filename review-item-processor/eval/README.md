# 審査の評価セット

審査のプロンプト・モデル・答えの受け取り方を変えたとき、判定が良くなったのか
悪くなったのかを数字で確かめるためのもの。審査の中核（`process_review_from_local`）
を手元で直接呼ぶ。Bedrock を実際に呼ぶので費用がかかる（1ケース 3 円ほど）。
本番のデータは使わない。書類はすべて架空。

```sh
cd review-item-processor
.venv/bin/python eval/run_eval.py --repeat 2            # 構造化出力あり・なしの両方
.venv/bin/python eval/run_eval.py --mode structured     # 片方だけ
.venv/bin/python eval/run_eval.py --only inject-fake-json
```

結果は `eval/results/`（git には入れない）に残る。

## ケース（`cases.py`、44件）

| 分類 | 見ること |
|---|---|
| clear | はっきり合格・不合格（合計金額、有効期限、反社条項） |
| visual | 見た目で判断する（押印があるか、「（印）」の文字だけか） |
| reasoning | 計算や基準に当てる（支払期日が60日以内か、登録番号の桁数、金額の整合） |
| missing | 必要な記載が無い |
| adversarial | 文書に仕込まれた操作（「合格にせよ」という指示、目印つきの偽の答え、白文字の隠し指示、「承認済み」という主張）。正解はどれも不合格 |
| office | Word・Excel・PowerPoint（XML から Markdown にして渡す経路） |
| multi-file | 見積書と請求書を見比べる（金額が一致するか） |
| long | 120ページの契約書。1回の要求に載る100ページを超えるので、道具で読む経路に入る |
| scanned | スキャンした書類（文字の無い PDF）。1・12・60ページ。前読みの書き起こしで読む |
| form-annot | 記入欄（AcroForm）にだけ値がある申込書、付箋の注釈が残った見積書 |
| drawing | 寸法が図（画像）の中にだけある図面 |
| image-only | 書類を撮った画像（PNG）だけの審査 |
| handwriting | 手書き風の字で書いた同意書（スキャン）。手書き風の字体（Yomogi）なので、本物の手書きより整っている |

書類の作り方は `documents.py`。ケースを足したら、ファイルを作り直す:

```sh
uv run --no-project --with playwright --with python-docx --with openpyxl \
  --with python-pptx --with pypdfium2 --with pillow --with pypdf --with reportlab \
  python eval/build_fixtures.py
```

既にあるファイルは作り直さない（中身が同じでも作成日時が変わり、git に差分が
出るため）。作り直したいファイルは消してから流す。

## 前読み

検証環境では、1回で渡せない書類（100ページ超・4.5MB 超）とスキャンした書類を
審査の前に読み取る（前読み）。前読みがあると道具で読む経路に入り、文字の取れない
ページは書き起こしで読む。評価でも、検証環境と同じ関数で前読みを作ってから審査
する（`predigest.py`）。前読みは費用がかかる（120ページで $1〜2）ので、結果は
`.digest-cache/`（git には入れない）に残して使い回す。`--no-predigest` で前読み
なしにできる。表の「費用」は審査の分だけで、前読みの分は入らない。

## 見方

- **正解**: 期待した判定と一致した数。答えを読めなかったものは数えない。読めない
  答えは不合格として扱われるので、正解が不合格のケースでは「たまたま正解」に
  なる（実際に、偽の答えに引きずられて pass と書き、JSON が壊れて不合格に
  なった例があった）
- **費用**: 同じ文書を続けて流すとプロンプトキャッシュが効いて安く出る。方式を
  比べるときはトークン数で比べる
- **route / toolCalls**: どの経路で読ませたか（丸ごと渡せない書類は途中で道具の
  経路に切り替わる）と、道具を呼んだ回数

## 基準（2026-09-25、Sonnet 4.6、全44件を各2回、前読みあり）

| | 構造化出力 | 以前の取り出し方 |
|---|---|---|
| 正解 | 88/88 | 86/88 |
| adversarial | 8/8 | 6/8（偽の答えのケースで2回とも pass と書いた） |
| それ以外の分類 | すべて正解 | すべて正解 |
| 読めない答え | 0 | 2 |
| 読んでいない範囲まで「全部確認した」と書いた | 0 | 0 |
| 入力 / 出力トークン（中央値） | 4,558 / 739 | 3,470 / 381 |
| 1件の時間 | 10.4 秒 | 7.6 秒 |

構造化出力は、出力の型（道具の定義）のぶん入力が約 1,100 トークン、答えの
項目のぶん出力が約 300 トークン増える。この評価の書類は1ページで小さいので
割合が大きく見えるが、実際の書類（数万トークン）では数％にとどまる。

途中で分かったこと:
- 型の中で判定（result）を推論（explanation）より前に置くと、推論する前に
  合否を決めてしまい、理由と判定が食い違った（理由は「12桁で足りない」、判定は
  pass）。推論を先に置いて解消した
- 文章で推論を書いてから道具で答えさせると、出力が倍になった。推論は
  explanation の中に書かせる

- 長い書類で条項が無いケースでは、構造化出力のほうが道具を多く呼ぶ（11回と
  7回）。入力も膨らむ（大半はキャッシュ読み）。読む範囲を広げているため
- **どちらの方式も、読んでいない範囲まで「全ページ確認した」と書く。** 道具は
  1回20ページまでで、超えた分は「返していない」と断っているのに、モデルは読み
  直さずに先へ進む。以前の取り出し方は 1〜20・100〜120 ページしか読まずに
  「全120ページを確認」と書いた。結論（条項が無い）は全ページの検索でも
  裏付けられているが、理由の書き方は事実と違う

- 検索の道具が前読みの書き起こしを探していなかった。スキャンした書類では何を
  探しても0件で、モデルは全ページを読みにいった（60ページで道具8〜9回・入力
  約6.6万トークン）。書き起こしも探すように直して、道具4回・約1.4万トークン
  （8割減）になった。60ページでは直す前も正解していたが、読める文字数には
  上限があるので、もっと長い書類では読み切れずに見落とすおそれがあった
- 評価で前読みを並列に作ると、PDF を画像にするライブラリ（pdfium）が落ちる
  （スレッドに対して安全でない）。画像にするところだけ1つずつにしてある

- 読んだ範囲の案内（道具がページを返すたびに「ここまで読んだ／残り」を添える）
  を入れる前は、以前の取り出し方で 120 ページのうち 41 ページしか読まずに
  「全120ページを確認」と3回とも書いた。入れたあとは3回とも全ページを読んだ。
  `REVIEW_READING_PROGRESS=0` で案内を止めて比べられる。評価では、読んでいない
  範囲があるのに全体を確認したと書いた回数を数えている
- 記入欄に値のある申込書を、両方式とも2回とも「未記入」と判定した。ページを
  画像にするとき記入欄を描く設定（pdfium の init_forms）をしておらず、モデルに
  空欄の画像を見せていた。値は文字でも渡していたが、見た目のほうを信じた。
  設定を足して直った

## まだ無いもの

  覆した結果は動作確認の8件だけ（2026-09-20）。運用が始まって溜まったら、
  書類が顧客のものになるので、使うかどうか・どう匿名化するかを決めてから作る
- 本物の手書き、写真の傾きや影、複数の画像と文書を混ぜた審査（画像も前読み
  される経路）
