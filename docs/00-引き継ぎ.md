# 引き継ぎ

このリポジトリを引き継ぐ方が最初に読む文書です。細部は各文書に書いてあるので、
ここでは全体の位置と、どこに何があるか、残っている課題をまとめます。

このリポジトリは公開です。環境の URL・AWS アカウント・テスト用アカウントの
パスワードなどは書いていません。別に受け渡します。

## このリポジトリは何か

[aws-samples/review-and-assessment-powered-by-intelligent-documentation](https://github.com/aws-samples/review-and-assessment-powered-by-intelligent-documentation)
（RAPID）のフォークです。社内の検証環境に載せて使うための修正を加えています。

| ブランチ | 役割 |
|---|---|
| `ops/deploy-office` | **検証環境に出しているもの。引き継ぎの中心**。修正はここに積む |
| `main` | 本家の `main` と同じに保つ（本家の取り込み用）。直接コミットしない |
| `fix/…`・`feat/…`（下の表） | 本家に出している PR。本家でマージされたら消してよい |
| `pr-assets` | 本家への PR #336 に載せた画面写真の置き場。PR が閉じるまで残す |

origin には、フォークしたときに本家から引き継いだだけのブランチ（`claude/issue-*`、
`dependabot/*` など）もあります。本家と同じ中身で、こちらでは使っていません。

## 変えたときの確かめ方

1. **テスト**: `backend` で `npx vitest run`、`review-item-processor` で
   `.venv/bin/python -m pytest -q`、`frontend` で `npx tsc --noEmit && npm run build`
2. **評価セット**（審査の判定・プロンプト・モデル・読み方を変えたとき）:
   `review-item-processor` で `.venv/bin/python eval/run_eval.py`。Bedrock を実際に
   呼ぶ（全件で $1〜2）。正解数に加えて「前読みが使われなかった」数を見る。1件でも
   あれば終了コード 2 で終わる。正解数だけでは見逃す不具合があった（eval/README 参照）
3. **デプロイ**: `./deploy.sh`。稼働時間内に、終了コードを必ず確かめる
   （docs/03-運用.md）
4. **デプロイ後の確認**: `scripts/verify-deploy/` の4本。全件 OK を確かめる

## 大事な決まり

- **権限**（docs/05-審査の流れ.md）: 審査は、見るのは同じ部署まで・直すのは作成者だけ。
  チェックリストとプロンプトは、見る・直すのは同じ部署まで・消すのは作成者と管理者だけ。
  ツール設定を作る・消す・プレビューするのは管理者だけ。判定は
  `backend/src/api/core/access/` に集めてある
- **アップロード**: 受け付ける拡張子は許可制で、Content-Type はサーバが決める
  （`backend/src/api/core/uploads.ts`）
- **ファイルの削除**: 審査・チェックリストを消すと S3 のファイルも消える。ほかがまだ
  使うファイルは残す（`backend/src/api/features/stored-files/`）
- **判定の受け取り**: 構造化出力（`review-item-processor/review_output.py`）。
  審査する文書は外から来るので、中の指示には従わせない
- **ログの保存期間は無期限**（意図的。docs/04-ログ.md）
- **Git**: `main` は本家と同じに保つ。コミットメッセージに「なぜ」を書く

## 残っている課題

優先度の高い順です。

1. **本家への報告が済んでいない（急ぎ）。** 2026-09-24〜25 に塞いだ権限とアップロードの
   穴（コミット `5dbe235`・`5f23552`）は本家にも同じものがある。本家には公開の Issue や
   PR ではなく、AWS の脆弱性報告の窓口か GitHub の非公開の報告で伝える
2. **API の Lambda の IAM が広い。** ナレッジベースのバケットを読むため、アカウント内の
   全バケットの `s3:GetObject` を持っている。取り出せる場所はアプリで絞ってあるが、
   権限そのものは広い（`cdk/lib/constructs/api.ts`）
3. **アップロードの時点では大きさの上限が効かない。** 上限は審査を作るときに確かめる。
   縛るには署名付き POST に変える必要がある
4. **再審査で引き継いだ合格が報告書で分からない。** 画面には「前回から引き継ぎ」と出るが、
   報告書には出ない。文書を差し替えても前回合格の項目は審査し直されない。
   根拠にした文書が差し替わった項目だけを審査し直すのがよい
5. **文書の中の指示に、モデルがまったく引きずられないとは言い切れない。** 判定は人が
   確かめる前提
6. **評価セットは架空の書類だけ。** 手書きは手書き風の字体、写真の傾きや影、画像と文書を
   混ぜた審査は入っていない。実際の運用で人が覆した結果が溜まったら、顧客の書類を
   使うか・どう匿名化するかを決めてからケースにする
7. **テスト用アカウントに名前の属性が無い。** 最終更新者などが「不明」と出る

## 経緯を知りたいとき

各コミットのメッセージに、何を・なぜ変えたか、どう確かめたかを書いてあります。
2026-09-24〜25 の主な変更は次のとおりです。

- 部署の権限（チェックリスト・プロンプト）、権限の穴5件、アップロードの許可制
- 着眼点が審査に届いていなかった不具合、判定を文書から操作させない守り
- 構造化出力と評価セット、検索が前読みの書き起こしを探すように、読んだ範囲の記録、
  記入欄を描く、前読みが検証環境で使われていなかった不具合（ジョブ ID の受け渡し）
- 審査・チェックリストを消したときにファイルも消す
