# 読み取り結果の持ち方

審査の前に書類を読み取った結果を、どこにどう置いているかの説明です。

## 二層に分けている

| 置き場所 | 中身 | なぜ |
|---|---|---|
| **S3** | 書き起こした本文、図の説明 | 大きい。検索もしない |
| **DB** | どこにあるか、何が読めたか | 問い合わせたい。壊れていないか確かめたい |

本文まで DB に入れると、100ページの書類で行が肥大します。逆に DB に何も
持たないと、**どの審査がどれを読んだかを SQL で追えません**。

## 以前はキーの規則だけで表していた

```python
key_for(document_key, job_id) = f"digest/{job_id}/{document_key}.json"
```

対応表を持たずに済む一方、**規則が守られている間しか成り立ちません**。

| 場面 | 起きること |
|---|---|
| ファイルの差し替え・キーの変更 | 結果が迷子になり、誰も消せない |
| ライフサイクルで消える | DB に痕跡が無いので気づけない |
| 「どの審査がどれを読んだか」 | キーを組み立てて総当たりするしかない |

いまは**実際に書いた値を行として残す**ので、規則が崩れても対応は残ります。

## 表の構成

```
ReviewDocument（審査に上げた書類）
   └─ 1対1 ─ ReviewDocumentDigest（読み取り結果の在り処と状態）
                 ├─ 1対多 ─ ReviewDocumentPage（ページごと）
                 └─ 1対多 ─ ReviewDocumentImage（画像ごと）
```

**`reviewJobId` は持ちません。** 書類から辿れるので、持つと二重管理になります。

### 状態は4つ

| 状態 | 意味 |
|---|---|
| `completed` | ページを全部読めた |
| `partial` | 一部のページが読めなかった |
| `failed` | ページはあったが1枚も読めなかった |
| `no_pages` | **読むページが無かった**（Office のようにページを持たない書類） |
| `not_needed` | **先読みが要らなかった**（小さい書類。審査時に元のファイルを直接渡す） |

`no_pages` を分けているのは、`completed` と混ぜると「読んだ結果、問題なし」と
区別できなくなるためです。`failed` は異常、`no_pages` は正常です。

`not_needed` は、**先読みを通らなかった書類にも行を残す**ためのものです。
行が無いままだと「不要だった」のか「記録に失敗した」のかが区別できません。
置き場所は無いので `s3Key` は空になります。

### 読めなかったページは行で持つ

以前は審査結果の JSON に配列で埋めていました。**チェック項目ごとに同じ内容を
書いていた**ので、200項目なら200回入ります。行にしたことで1回になり、
SQL でも問えるようになりました。

```sql
-- 読めなかったページを持つ審査
SELECT j.name, d.filename, p.page_number
FROM review_document_pages p
JOIN review_document_digests g ON g.review_document_digest_id = p.digest_id
JOIN review_documents d ON d.review_document_id = g.review_document_id
JOIN review_jobs j ON j.review_job_id = d.review_job_id
WHERE p.was_read = 0;
```

## 誰が書くか

読み取り Lambda（Python）は **DB に繋いでいません**。S3 と Bedrock だけを見ます。
そのため、状態機械で1段挟んで TypeScript 側に渡します。

```
StoreReading（Python）   S3 に書き、「どこに何を書いたか」を返す
   ↓
RecordReading（TypeScript）  受け取って DB に残す
```

Python 側に Prisma を持たせる案もありましたが、VPC・秘密情報・スキーマの
二重管理が増えるので採りませんでした。

## 落ちても審査は止めない

記録に失敗しても審査は続けます。記録が無くても S3 の中身はあるので判定は
できます。ここで止めると「読み取りは使えるのに審査ができない」ことになります。

ただし**対応する書類が見つからない場合は `skipped` に残して警告**します。
黙って捨てると、対応が壊れていることに気づけないためです。

## ジョブをまたいで使い回さない

読み取りは**そのジョブのチェックリストを踏まえて書く**ので、別のチェックリストの
審査に持ち越すと、見るべき観点がずれたものを根拠にすることになります。書類が
差し替わっていないかもここでは分かりません。読み直す費用より、古いものを黙って
使う危うさのほうが高いという判断です。
