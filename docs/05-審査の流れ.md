# 審査の流れ

[01-全体像.md](01-全体像.md) が「どこに何があるか」なら、この文書は**どこで何を
判定し、外れたときにどうするか**です。判定の基準値をここに集めてあります。
コードを読む前の地図として使ってください。

## 1. ファイルのアップロード

画面はファイル本体を API に流しません。

```
画面 → POST /documents/review/documents/presigned-url → 署名付きURL
画面 → PUT（S3へ直接）
画面 → POST /review-jobs（S3のキーだけを渡す）
```

大きいファイルが API を通らないので、API の要求上限にも実行時間にも縛られません。

## 2. ジョブ作成の門番

`backend/src/api/features/review/usecase/review-job.ts` の `validateJobDocuments`。

| 見るもの | 基準 | 外れたとき |
|---|---|---|
| 件数 | 1件以上・20件以下（`MAX_REVIEW_DOCUMENTS`） | エラー。作らせない |
| 大きさ | PDF 100MB / Office 30MB / 画像 20MB / その他 4.5MB | `FileSizeExceededError` |
| S3 に無い等 | — | **警告だけ出して通す**（後段で落ちる） |

通ったら **DB に保存してから** SQS に送ります。順序が逆だと、まだ保存されていない
ジョブを準備処理が更新しようとして失敗します。SQS 送信に失敗したジョブは待ちのまま
残さず `FAILED` にします。

## 3. キューから実行へ

`cdk/lib/constructs/review-queue/consumer/handler.py` が同時実行数を自分で絞ります。

| 状況 | どうするか |
|---|---|
| 走っている実行が `REVIEW_MAX_CONCURRENCY`（既定 2）に達している | 可視性 15 秒に戻して再挑戦 |
| キューでの待ちが `MAX_QUEUE_WAIT_MS`（既定 24 時間）を超えた | 審査せず `QUEUE_TIMEOUT_ERROR` |
| 同じメッセージが二度届いた | 実行名が `messageId` なので `ExecutionAlreadyExists`。握りつぶして成功扱い |

処理を始めたら可視性を 1200 秒にします。

## 4. 段の並び

```
PrepareReview → PlanReading → ReadDocuments(Map) → StoreReading → RecordReading
              → ProcessAllItems(Map) → FinalizeReview
```

### PrepareReview — 何を審査するか

`selectItemsToReview` が2つ落とします。

- **子を持つ親項目**。子の結果から集計するので、モデルには聞かない
- **すでに `COMPLETED` の結果**。再審査のジョブで元のジョブから引き継いだもの

### PlanReading — 先に読むかどうか

モデルを呼ばずに決めます。種類ごとに基準が違います。

| 種類 | 先に読む条件 | 区切り |
|---|---|---|
| PDF | ページ数 > 100、または 4.5MB 超、または**どれか1ページでも文字が20字未満**（`SCANNED_PAGE_CHARS`。スキャンとみなす） | 20ページごと |
| Office | 埋め込み画像が **4枚以上**（`IMAGES_WORTH_DESCRIBING` = 3 を超える） | 20枚ごと |
| 画像 | 単体では読まない。**ジョブが道具経路に入る**か、他に読む書類がある、または**枚数 > 5**（`MAX_IMAGES_PER_REVIEW`） | 1枚ずつ |

Office の文字は XML からそのまま取れるので、読むのは埋め込み画像だけです。

「ジョブが道具経路に入るか」（`uses_tools`）は**書類1件ずつでは決まりません**。
ページ数の上限はジョブ全体の合計で効くので、40ページの PDF が3件あれば、どれも
単体では収まるのにジョブは収まりません。

条件に当たらなければ `tasks` は空、Map は0回、`store` は何もしません。
**普段の審査に費用も時間も足しません。**

### ReadDocuments / StoreReading / RecordReading

Map で並行に読み、結果は**戻り値ではなく S3** に置きます。Step Functions の状態は
256KB 上限で、20ページ分の書き起こしだけで数十KB になるため、持ち回ると確実に溢れます。

`RecordReading` が DB に索引を残します。状態は5つです。

| status | 意味 |
|---|---|
| `completed` | 計画したぶんを全部読めた |
| `partial` | 一部が読めなかった。読めなかったページは行で残る |
| `failed` | 読み取りそのものが落ちた |
| `no_pages` | 読む対象が無かった |
| `not_needed` | 先読みが要らなかった。`s3_key` は無い |

**この4段は落ちても審査を止めません。** 各段に `addCatch` を置いて
`ProcessAllItems` へ進みます。読めなくても元のファイルを見れば判定できるからです。
このとき `resultPath` を捨てるのが要点で、捨てないとエラーの中身が状態を丸ごと
置き換え、次の段が必要とするデータが消えて実行ごと落ちます。

## 5. 項目ごとの判定

項目1つにつき **前処理(TS) → 審査(Python) → 後処理(TS)** の3段です。

### 前処理

利用者の言語、項目名・説明・`reviewGuidance`・`feedbackSummary`、書類の S3 パス、
ツール設定、モデル ID を集めます。モデル ID が `availableModels` に無ければ黙って
既定へ落とします。

### 渡し方を決める

```
読み取り済みの結果がある（かつ画像審査でない） → 道具で読ませる
                              ↓ なければ _choose_route
引用が無効／モデルが文書ブロック非対応 → file_read
記入値や注釈のある PDF がある        → document_tools
画像あり ＋ 文書も混在                → document_block
画像だけ                             → file_read（拡大・切り出しができる）
それ以外                             → document_block
```

`document_block` で送って上限に当たったら `RequestTooLargeError` を捕まえて
`document_tools` に落ちます。

「記入値や注釈のある PDF」を分けているのは、そのまま渡すと記入内容が読まれるか
分からず、読まれなければ**空の申込書を審査する**ことになるからです。道具の経路
なら、こちらで読み出して本文に足せます。

### 合否そのもの

モデルが JSON で返します（`review_prompts.py`）。プロンプトが縛るのは3点です。

- **書類と道具で得た情報だけで判断する。** 事前知識・推測を使わない
- **情報が見つからなければ `fail`・`confidence` 0.40。** 説明に「何が見つから
  なかったか」を書き、`extractedText` と `sources` は空にする
- `confidence` の目安

| 範囲 | 意味 |
|---|---|
| 0.90〜1.00 | 明確な証拠がある |
| 0.70〜0.89 | 証拠はあるが多少の不確かさがある |
| 0.50〜0.69 | 証拠が曖昧 |
| 0.30〜0.49 | 判断できるだけの根拠が無い |

### 答えの受け取り方

答えは**構造化出力**で受け取ります（`review-item-processor/review_output.py`）。
出力の型（Pydantic）を出力用のツールとしてモデルに渡し、答えはそのツールの入力として
届きます。判定は `"pass"` / `"fail"` の列挙型、自信度は 0〜1 の数でしか返せません。
審査する文書の中に答えのような文字列があっても、答えとは別に届きます。

- 型の中では**推論（explanation）を判定（result）より前**に置いています。判定が
  先だと、推論する前に合否を決めてしまい、理由と判定が食い違いました
- モデルが最後まで出力用のツールを呼ばなかったときだけ、構造化出力なしでやり直し、
  返答の文章から JSON を取り出します（以前の方式）。そのときは**最後の**
  `<<JSON_START>>…<<JSON_END>>` を採ります。スロットリングなど、ほかのエラーでは
  やり直しません（黙って二重に払うことになるため）
- `REVIEW_STRUCTURED_OUTPUT=0` で以前の方式に戻せます。評価セットで比べるために
  残してあります（`review-item-processor/eval/README.md`）
- 最後に `_validate_and_complete_result` が欠けた欄を埋めます。判定が
  `"pass"` / `"fail"` でなければ不合格にして、読めなかったことを理由に書き添え、
  自信度が無ければ 0.5 にします。サーバの後処理（`post-review-item.ts`）でも
  判定をそろえます

## 6. 根拠の位置（sources）

判定の根拠は `sources: [{file, page, section, label}]` で受け取ります。
`_normalize_sources` が形の崩れたものを捨て、ページと節番号は**1以上の整数だけ**、
`label` は80字までを残します（`label` は場所の欄で、本文の抜き書きを入れる欄では
ないため）。

ページという単位はすべての書類にあるわけではないので、書類の種類ごとに
表し方を変えています。

Word にページ番号が無いのは実装の手抜きではありません。`.docx` はページ割りを
保存せず、表示するソフトが計算します。ファイルから読めるのは明示的な改ページだけで、
`word.py` はそれを改行として扱っています。Word の位置は見出しで表すのが妥当です。

| 形式 | 位置の表し方 | どこに入るか |
|---|---|---|
| PDF | ページ番号 | `page` |
| PowerPoint | `## Slide 3: 表題`（`powerpoint.py`） | `label`、道具経路なら `section` も |
| Excel | `## Sheet: 売上`（`excel.py`） | `label`、道具経路なら `section` も |
| Word | 見出し階層（`heading 1`〜`9`） | `label`、道具経路なら `section` も |
| 画像 | — | どれも入らない |

Word にページ番号が無いのは実装の手抜きではありません。`.docx` はページ割りを
保存せず、表示するソフトが計算します。ファイルから読めるのは明示的な改ページ
だけで、`word.py` はそれを改行として扱っています。Word の位置は見出しで表すのが
妥当です。

`section` は `list_documents` が振った節番号で、道具の経路で読んだときだけ入ります。
文書ブロックの経路には節番号が無く、見えるのは本文中の見出しだけなので、
**どちらの経路でも入るのは `label`** です。`section` を前提にした処理は書けません。

PDF に `label` や `section` を付けないのは、ページで足りるからだけでなく、
結果画面が Office のファイルから PDF のページを切り出そうとするのを防ぐためです
（`source-documents.ts` で振り分けています）。

## 7. 親項目への集約

`review-result-cascade-update.ts` が子から親へ遡ります。

- **子が全部 `COMPLETED` になって初めて**親を確定する
- **全員 pass なら pass、1つでも fail なら fail**
- 親の `confidence` は**子の最小値**
- 親の説明は「以下の子項目が不適合です: ◯◯、△△」と自動生成

## 8. 締め（FinalizeReview）

コストを集計したあと、**判定の付いていない項目が残っていないか確かめ、残っていたら
完了にせず落とします**。残したまま完了にすると、人は全項目を見たつもりで書類を
通してしまうためです。

## 9. 人が覆す

`PUT /review-jobs/:jobId/results/:resultId` で、コメントと「覆した理由」を付けて
上書きできます。

- 所有者（または管理者）だけ
- **再審査で置き換わったジョブの判定は変えられない。** 変えても新しいジョブには
  伝わらず、同じ項目が食い違って見えるだけになる。画面でボタンを隠すうえ、
  API を直に叩かれても通らないようにしてある

覆した理由を残しているのは、傾向から「AI のどこが外れるか」を読むためです。

## 10. 部署と見える範囲

誰がどの審査を見られるかは、その人の**部署**で決まります。兼務があるので、
所属は常に複数ありうるものとして扱います。

### 所属をどこから読むか

読み取りは `backend/src/api/core/access/departments.ts` の1か所に閉じてあります。IdP ごとに区切り方が
変わっても、この関数だけを直せば済みます。

**部署は Cognito のカスタム属性 `custom:departments` に入ります。**
兼務があるので値は複数で、区切りは `,` `;` 空白のいずれでもかまいません。

```
custom:departments = "sales,legal"      → 営業と法務を兼務
custom:departments = "sales; legal"     → 同じ
custom:departments = ""                 → 部署なし
```

**グループ（`cognito:groups`）は見ません。** グループは役割の管理に使うので、
部署を同じ入れ物に混ぜると、役割を足したつもりで見える範囲が変わります。

### 作るとき

審査ジョブ・チェックリスト・プロンプトのどれを作るときも、同じ規則で部署を
決めます（`resolveDepartment`）。画面の選択欄は `frontend/src/components/DepartmentPicker.tsx`
にまとめてあり、3つの作成画面が同じ部品を使います。プロンプトは**作るときだけ**
選ばせ、編集では部署を変えません（共有先が動くと、見えていた人から黙って消えるため）。


兼務の人の審査を、どちらの部署のものとして記録するかは**決められません**。
営業と法務を兼ねる人の審査を、法務の同僚に見せてよいとは限らないからです。

| 所属 | 画面で選んだか | どうなるか |
|---|---|---|
| 1つ | — | その部署 |
| 兼務 | 選んだ | 選んだ部署 |
| 兼務 | 選んでいない | **エラーで止める** |
| 兼務 | 属していない部署を送ってきた | **エラーで止める** |
| 無し | — | 部署なしで作る |

黙って片方へ寄せると見せたくない相手に見え、黙って部署なしで作ると同僚の履歴に
出てこないことに誰も気づけません。どちらも静かに起きるので止めます。画面でも
選ばせますが、API を直に叩かれても通らないようにしてあります。

### 見るとき

この規則は**審査ジョブ・チェックリスト・プロンプト**の3つに共通です。判定は
`backend/src/api/core/access/visibility.ts` に集めてあり、3機能とも同じ関数を
通ります。1か所にまとめてあるのは、繋ぎ忘れた画面だけ部署が効かない、という
気づきにくい不具合を防ぐためです（`core/access/shared-by-department.test.ts` で
配線を確かめています）。

ツール設定だけは部署で分けません。中身は「どのナレッジベースを使うか」といった
能力で、チェックリストの項目から名前とリンクが張られているため、部署で絞ると
「見えるチェックリストの中の開けないリンク」が生まれます。代わりに、**全員が
見られて、作成・削除・プレビューは管理者だけ**にしています（`assertIsAdminOrThrow`）。
プレビューは設定に書かれた `command` を API の Lambda でそのまま実行するので、
管理者以外に開くと、誰でも DB の認証情報や S3 を読める権限でコマンドを
動かせてしまいます。


| | 一覧・詳細 | 判定の変更・再審査・中止・削除 |
|---|---|---|
| 自分の審査 | 見える | できる |
| 同じ部署の審査 | **見える** | **できない** |
| 違う部署の審査 | 見えない | できない |
| 管理者 | 全部見える | できる |

兼務なら、**どちらの部署の審査も見えます**。見えることと直せることを分けて
いるのは、混ぜると「公開したとたんに他人が判定を書き換えられる」からです。

### チェックリストは同じ部署の人も直せる

チェックリストは審査と規則が違います。審査の判定は「誰が決めたか」を残すために
始めた人しか変えられませんが、チェックリストは部署で使い回す道具です。作った人が
異動・退職したあとも、部署の人が保守を続けられないと困ります。

| | 見る・審査に使う・複製 | 項目・着眼点・重要度などを直す | 削除 |
|---|---|---|---|
| 作成者 | できる | できる | できる |
| 同じ部署の人 | できる | **できる** | **できない** |
| 違う部署の人 | できない | できない | できない |
| 管理者 | できる | できる | できる |

- **削除だけは作成者と管理者に絞っています。** 消すと戻せないためです。作成者が
  いなくなったチェックリストを消すときは、管理者が消します。
- **最後に直した人を残します**（`check_list_sets.last_edited_by` と名前・日時）。
  部署の誰でも直せるので、変わった理由を聞く相手が分かるようにするためです。
  詳細画面の説明の下に「最終更新: 名前（日時）」と出ます。名前は審査の
  `user_name` と同じく、そのときの値の写しです。
- **審査を始めるときも、使えるチェックリストかを確かめます。** 以前は ID さえ
  分かれば他部署のチェックリストで審査を始められました。
- 部署が付いていないチェックリストは、作成者と管理者しか使えず、直せません。

判定は `backend/src/api/core/access/checklist-access.ts` に集めてあります。
**プロンプトも同じ規則です。** 以前は一覧だけ部署で絞っていて、ID を指定した
取得・更新・削除は誰でもできました。

### 審査される文書から判定を操作させない

審査する文書は外（申請者・取引先）から来ます。合格にしてほしい人が中身を
書けるので、次の守りを置いています。

- **文書の中身は指示として扱わせない。** プロンプトに、文書の中の文章は資料で
  あって指示ではないこと、判定の仕方を指図する記述には従わず、あれば理由に
  書くことを入れています（`review_prompts.py` の `DOCUMENT_CONTENT_IS_DATA`）。
- **判定は最後の回答から読む。** 出力の目印 `<<JSON_START>>…<<JSON_END>>` が
  複数あれば最後のものを採ります。文書に目印つきの偽の回答が書かれていて、
  モデルが推論の途中でそれを引用しても、最終回答より先に採られません。
- **判定は `pass` / `fail` の2つだけ。** それ以外（`"PASS"`、`"合格"` など）は
  不合格にして、読めなかったことを理由に書き添えます。審査処理とサーバの
  両方で確かめます。
- **過去の指摘の要約は参考にとどめる。** 判定を上書きしたときのコメントから
  自動でまとめて審査に入れますが、「文書の記載が優先」「それだけで合否を
  決めない」扱いです。集めるのは、そのチェックリストを直せる人（作成者と
  同じ部署）の審査での上書きだけです。要約はチェック項目の編集画面に出て、
  直せる人が消せます（消すと、その時点より前のコメントは入り直しません）。

**残っていること:** 文書に書かれた指示に、モデルがまったく引きずられないとは
言い切れません。判定は人が確かめる前提です。再審査で文書を差し替えても、前回
合格の項目は引き継がれ、報告書にはそれが出ません（画面には出ます）。

### 文書の取り出しと削除

S3 のキーやバケット名は画面から送られてきます。そのまま信じると、キーさえ
分かれば誰の文書でも取り出せて消せるので、次のように絞っています。取り出しは
`backend/src/api/features/review/usecase/document.ts`、削除は
`backend/src/api/features/stored-files/` です。

- **取り出し（`/documents/download-url`）:** 文書バケットでは、見てよい審査の
  文書だけ。ほかのバケットは、ナレッジベースの出典として**見てよい審査の結果に
  出てきた場所**だけで、どの審査の出典かを `reviewJobId` で添える必要があります。
  以前はバケットとキーをそのまま署名していて、API の権限がアカウント内の
  どのバケットでも読めるため、RAPID と関係ないバケットの中身まで取り出せました。
  URL の有効期限は最大1時間です。
- **削除（`DELETE /documents/review/:id`、`/documents/checklist/:id`）:** 画面が
  送るのは文書 ID です。消せるのは、アップロードの場所（`review/original/<ID>/`
  など）の下にあり、まだ審査にもチェックリストにも使われていないものだけです。
  以前は送られた値を S3 のキーとしてそのまま消していました。
- **審査・チェックリストを作るとき:** 文書のキーが、その文書 ID のアップロードの
  場所を指しているかを確かめます。他人がアップロードした書類のキーを書いて
  審査にかけることはできません。
- **審査・チェックリストを消したとき:** DB の行を消したあとで、その S3 のファイルも
  消します。以前は行だけが消え、申込書などの中身が残り続けました。
  - 審査: 元の書類・画像（ほかの審査がまだ指していなければ。再審査は元の審査の
    文書を引き継ぐため）、前読みの書き起こし（`digest/<ジョブID>/`）と途中経過
  - チェックリスト: 元の書類（ほかのチェックリストがまだ指していなければ。複製は
    複製元のファイルを共有するため）と、そこから作ったページの画像・読み取り結果など。
    チェックリストを消すと、それを使った審査も一緒に消えるので、その審査のファイルも
    消します
  - ファイルを消せなくても削除は成功させ、残ったキーをエラーとしてログに残します

- **受け付ける種類:** アップロード先を発行するときに拡張子を許可制にし、
  Content-Type はサーバが拡張子から決めます（`backend/src/api/core/uploads.ts`）。
  審査は PDF・Office・画像、チェックリストは PDF・Office・txt・md・csv です。
  審査・チェックリストを作るときも同じ一覧で確かめます。以前は `.html` を
  `text/html` として上げられ、「開く」で S3 のドメインのままスクリプトが動きました。
- **開き方:** ダウンロード URL では Content-Type と Content-Disposition を拡張子から
  決め直し、PDF と画像以外はブラウザで開かせず保存させます。許可制より前に
  上がったファイルや、ナレッジベースのバケットのファイルにも効きます。

**残っていること:** アップロードの時点では大きさの上限が効きません（上限は
審査を作るときに確かめます）。署名付き PUT では大きさを縛れないためで、
縛るにはサイズ上限付きの POST に変える必要があります。また API の Lambda の IAM は、ナレッジベースのバケットを読むために
アカウント内の全バケットの `s3:GetObject` を持ったままです。上の判定で
取り出せる場所は絞ってありますが、権限そのものは広いままです。ナレッジベースの
バケットが決まっているなら、`cdk/lib/constructs/api.ts` の対象を絞ってください。

一覧の条件に「自分が開始した審査」を残しているのは、部署が付かない審査がある
ためです。どこにも属していない人の審査や、部署機能より前の審査には
`departmentId` が入りません（後から埋まりません）。部署だけを条件にすると、
それらが作った本人からも見えなくなります。

**費用のページは一覧と見え方が違います。** 一覧には同じ部署の同僚の審査も
出ますが、費用は自分のぶんだけです（`getReviewCostSummary` は `ownerUserId`
でしか絞りません）。管理者だけが全体を見られれば足りる、という判断でそうして
あります。

### 部署が付かない審査

部署は必ず入るとは限りません。次のいずれでも、審査は `departmentId` なしで
作られます。

- 部署を使わない運用
- その人にまだ部署が設定されていない
- 部署の仕組みより前に作られた審査（後から埋まりません）

そういう審査は**作成者（と管理者）にしか見えません**。同僚の履歴には出ないので、
「共有したはずなのに見えない」となったら、まず部署が付いているかを見てください。

費用の内訳では、部署の付いていない審査は**部署別の表に入れません**。「未所属」と
いう部署があるように見せると、実在する部署と並んで紛らわしいからです。ただし
**合計には入る**ので、内訳を足しても合計に届きません。その差は表の下に
「この内訳には、部署の付いていない審査 N 件（$X）を含みません」と出ます。

管理者に部署が入っても、**見える範囲は全件のままです**。部署は「その審査が
どの部署の仕事か」を記録するだけで、管理者の権限を狭めません。

これらの配線は `__tests__/department-scenarios.test.ts` で確かめています。
単体の判定が正しくても、呼ばれていなければ意味がないためです。

### Cognito 側の設定

`cdk/lib/constructs/auth.ts` で2つ設定しています。

| 設定 | 値 | なぜ |
|---|---|---|
| `customAttributes.departments` | `StringAttribute({ mutable: true })` | SAML の属性マッピングは、写す先が mutable であることを求める |
| クライアントの `readAttributes` | `custom:departments` を含む | 読めないと ID トークンに載らない。載らなければ部署は無いのと同じ |

**属性は後から直せません。** Cognito は「足す」ことはできますが、既存の属性を
変えることも消すこともできません。`mutable` の指定はここで決め切る必要があります。

なお、`mutable` を省くと Cognito 側の既定で `true` になります（実際、指定して
いない `rapid_role` も実環境では `Mutable: true`）。それでも `departments` には
明示してあります。既定に頼ると、CDK や Cognito の既定が変わったときに、
**直せない属性が黙って `false` で作られる**からです。

なお、属性を足すだけならユーザープールは**置き換わりません**（`Schema` の更新は
無停止）。既存の利用者は消えません。

### 引き継ぐ人が知っておくこと

1. **部署を管理する画面はありません。** いまは AWS CLI か Cognito のコンソール
   から属性を書きます。本番では IdP 側の運用に載せる前提です。

   ```
   aws cognito-idp admin-update-user-attributes \
     --user-pool-id <pool> --username <user> \
     --user-attributes Name=custom:departments,Value=sales,legal
   ```

2. **`custom:departments` は書ける側（`writeAttributes`）に入れていません。**
   入れると、利用者が自分のアクセストークンで自分の部署を書き換えられます。
   部署は見える範囲を決めるので、自分で足せるなら他部署の審査が読めます。

   その代わり、**SAML で部署を IdP から写す運用にするときは、ここに足さないと
   Cognito がサインインのたびに書き込みに失敗します。** 「IdP から入れられる
   こと」と「本人が書き換えられないこと」は Cognito の同じ設定で決まるので、
   両立しません。IdP を繋ぐときに選んでください。属性の自己書き換えを許せない
   なら、部署を Cognito ではなくこの製品の DB で持つ形に変える必要があります。
