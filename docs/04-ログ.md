# ログ

調査しやすさを優先した設計です。開発中はすべて出し、本番では絞れるようにして
あります。

## 保存期間は無期限（意図的）

**縮めないでください。** 短くすると、後から「あの審査で何を読んだか」を
確かめられなくなります。誤って短い期間を設定すると、法令や契約で求められる
保存を満たせなくなる恐れがあります。

費用を理由に縮めたくなったときは、**期間を決める前に、何をどれだけ残す義務が
あるかを確認してください**。CDK でも Lambda のロググループには保存期間を
指定していません（API Gateway のアクセスログなど、一部だけ1週間）。

## どの審査の話かが必ず分かる

審査は項目ごとに並行して走ります。ログだけ見て「どの審査のどの項目か」が
分からないと、CloudWatch で追えません。

そこで**入口で一度だけ文脈を覚えさせ、以降のすべてのログ行に自動で添えます**。

```
[job=01M33ZB... check=01M340... result=01M33Z...] 読み取りを始めた
```

呼ぶ側は今までどおり `logger.info(...)` と書くだけです。94箇所ある呼び出しを
書き換える必要はありません（`review-item-processor/logger.py`）。

### CloudWatch での追い方

```
fields @timestamp, @message
| filter @message like /job=01M33ZB6R8TK8EN87RRJVPGJJW/
| sort @timestamp asc
```

項目を1つだけ追うなら `check=` を足します。

## 水準は環境変数で切り替える

`LOG_LEVEL` を見ます。既定は `DEBUG`。

| | |
|---|---|
| 開発中 | `DEBUG` のまま。全部見える |
| 本番 | `INFO` にすればデバッグ出力が消える（**コード変更は不要**） |

以前は `logger.py` で `DEBUG` に固定しており、本番でも全部出る状態でした。

## 書くときの決まり

- **新しいログには、追える手がかりを添える。** 文脈は自動で付くので、
  それ以外に必要なもの（ファイル名、件数など）を書く
- **配列やオブジェクトを丸ごと出さない。** 件数だけにする。200項目の
  チェックリストで毎回それだけの文字列を組み立てることになる
- **分岐したことを言い直さない。** 直上のコードを読めば分かる内容は書かない
- **水準を使い分ける。** 調査用は `debug`、節目は `info`、想定外は `warning`
  以上。`print` は使わない

## 道具が呼ばれたかが残る

モデルに道具を渡しても、呼ぶとは限りません。呼ばれていないのか、呼ばれたが
中身が足りなかったのかを区別できるよう、記録を残しています。

```
[document tool] read_pdf_pages file=申込書.pdf first=1 last=1 chars=312
```

注釈が読まれない不具合は、**この記録が無くて原因にたどり着けませんでした**。
入れた直後に「道具が1度も呼ばれていない」ことが分かり、原因が特定できました。
