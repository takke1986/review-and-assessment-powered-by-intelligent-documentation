# 部署ごとに審査履歴を分けるための準備メモ

実装はしていない。**あとから作れることを確かめた記録**と、作るときの設計。

## 背景

- 100名規模・複数部署での利用を想定
- 「部署ごとに審査履歴を管理したい」
- **兼務がある**ので、1人が複数の部署に属する
- **本番は SAML 認証**（部署情報は IdP 側が持つ）

## 確かめたこと：ユーザープールは作り直されない

一番の懸念は、Cognito ユーザープールに属性を足すと**プールごと作り直され、
利用者が全員消える**ことだった。このプールは `removalPolicy: DESTROY` なので
実際に消える。

試しに `custom:departments` を足して `cdk diff` を取ったところ、

```
[~] AWS::Cognito::UserPool Auth/UserPool
 └─ [~] Schema
     └─ [+] { "Name": "departments", ... }
```

**`may be replaced` が付かない**。その場での変更として扱われる。
つまり、利用者を抱えたまま安全に足せる。

（確認日: 2026-09-20 / aws-cdk-lib 2.260.0 / CLI 2.1128.1）

## 設計

### 所属の持ち方

SAML なら部署は IdP から来る。Cognito の属性マッピングで
`custom:departments` に入れる。**兼務があるので複数値**になる。

多値の SAML 属性が Cognito の文字列属性にどう入るかは IdP 実装で変わるため、
**実際の IdP で確かめてから**区切り文字を決めること。ここを推測で決めない。

### ジョブがどの部署のものか

兼務があるので「作った人の所属」だけでは決まらない。営業と法務を兼ねる人の
審査を、法務の同僚に見せてよいとは限らない。

案は2つ。

1. **作るときに選ばせる** — 「この審査は営業部として行う」。所属が1つなら
   選択肢も1つなので、手間はほぼ増えない。意味は正確
2. **作った人の所属すべてに紐づける** — 手間はゼロだが、上のような
   見せたくない組み合わせが起きる

**1を推す。** 履歴を部署ごとに分ける目的からして、どの部署の仕事かが
決まっていないと意味をなさない。

### 実装の当たり

- `ReviewJob` に部署の列を1つ（`sharedWithOrg` と同じ要領）
- 見える範囲の判定は `review-job-visibility.ts` に集約済み。
  「自分のもの ＋ 自分の所属部署のもの」に条件を足すだけ
- 認証の入口（`auth.ts` middleware）は `cognito:groups` を既に読んでいる。
  属性方式にするならここに1行足す
- 一覧の絞り込みは `checkListSetId` と同じ形で増やせる
- 費用の内訳も、チェックリスト別と同じ作りで部署別を足せる

1日程度の見込み。土台は今日の作業（見える範囲の集約・絞り込み・費用の内訳）で
できている。

## 注意

- 共有の切り替えは画面から外してある（承認と他部署連携は製品の外で運用する
  ため）。仕組み（列と API）は残っているので、部署単位の共有に作り替える
  土台として使える
